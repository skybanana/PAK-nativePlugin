# 판정 안정성 실험 정리

## 목적

`PracticeModeFingeringTest`의 코드 판정이 반복 연주 후 불안정해지는 원인을 찾고,
단독 입력 테스트인 `chordOnsetTest`와의 차이를 확인한다.

## 관찰된 현상

- `FingeringPractice.log`에서는 초반에 G5/C5를 통과하다가 뒤로 갈수록 같은 코드를
  연주해도 실패가 연속 발생했다.
- `chordOnsetTest`에서는 같은 코드를 반복 입력해도 플러그인보다 높은 빈도로 통과했다.
- `FingeringPractice2.log`에서 Target 10 부근부터 chord pass는 9에서 멈추고 fail만
  증가했다.

## 실험과 결과

### 1. 스피커 출력 영향

스피커를 끈 상태에서도 같은 문제가 발생했다.

- 결론: 모니터 출력의 음향 피드백은 주원인에서 제외한다.

### 2. 판정 창 기준 시각

`chordOnsetTest`는 onset을 감지한 callback 시각부터 160 ms를 수집한다.
`judgeWindowTest`는 플러그인처럼 `aubio_onset_get_last_s() + 160 ms`를 deadline으로
사용한다.

| 테스트 | 판정 수 | 통과 | 실패 | 통과율 | 캡처 크기 |
| --- | ---: | ---: | ---: | ---: | --- |
| `chordOnsetTest` 앞 53회 | 53 | 34 | 19 | 64.2% | 61~62 block, 7808~7936 sample |
| `judgeWindowTest` | 53 | 36 | 17 | 67.9% | 58~59 block, 7424~7552 sample |

플러그인 방식이 3~4 block 짧게 캡처했지만 통과율 차이는 2회뿐이었다. 서로 다른 연주
세션의 결과이므로 이 차이를 유의미한 성능 차이로 볼 수 없다.

- 결론: onset timestamp를 deadline으로 쓰는 방식은 캡처 길이를 바꾸지만, 이번 문제의
  주원인은 아니다.

### 3. AudioBlock queue 유실

`PracticeModeFingeringTest`에 `droppedAudioBlocks`를 출력해 확인했다.
`FingeringPractice2.log`에서 이 값은 0에서 211까지 증가했다. 반면 `droppedJudgeEvents`는
0이었다.

`droppedJudgeEvents`는 Unity로 전달할 판정 이벤트 큐의 상태이고,
`droppedAudioBlocks`는 callback에서 judge thread로 전달하는 실제 입력 음원의 유실이다.
따라서 두 값은 구분해서 봐야 한다.

- 결론: chord FFT와 pending judgment 처리 중 judge thread가 입력 속도를 따라가지 못해
  8-block audio queue가 차고, 실제 입력 block이 유실된다. 이는 플러그인이 단독 테스트보다
  불안정한 확정 원인이다.

### 4. 잔향 onset 선점

`chordOnsetTest`는 수집 중에도 `aubio_onset_do()`를 계속 실행하며 다음 값을 출력한다.

- `detected`: 감지된 전체 onset 수
- `started`: 실제 chord 수집을 시작한 횟수
- `ignored while collecting`: 이미 수집 중이라 무시된 onset 수

대부분의 단독 테스트 구간에서 `detected == started`이고 `ignored while collecting == 0`이었다.
후반에 무시된 onset은 1회뿐이었다.

- 결론: 잔향 onset은 존재할 수 있으나, 단독 테스트에서 보인 연속 chord 실패의 주원인은 아니다.

### 5. C5 코드로 단독 테스트 전환

`chordOnsetTest`의 검사 대상을 G5에서 C5(C3 + G3)로 변경했다. C5에서도 간헐적 또는
연속 실패가 남았다. 즉 차트의 코드 종류만으로 플러그인과 단독 테스트의 차이를 설명할 수 없다.

현재 fundamental 판정은 각 목표 음의 탐색 범위에서 가장 큰 FFT bin이 계산된 중심 bin과
정확히 같을 때만 통과시킨다.

```cpp
if (strongestBin != centerBin)
    return false;
```

저음 fundamental은 기타의 미세한 튜닝, 프렛 압력, 피킹 직후 pitch bend, harmonic 비율 변화에
따라 peak가 인접 bin으로 이동하기 쉽다. 이 경우 주변 에너지가 충분해도 즉시 실패한다.

- 결론: AudioBlock 유실과 별개로 exact-bin 조건은 단독 테스트의 간헐적·연속 실패를 만드는
  유력한 원인이다.

## 최종 결론과 우선순위

1. **AudioBlock queue 유실을 먼저 해결한다.** 플러그인과 단독 테스트 사이의 안정성 차이를
   만드는 직접 원인이다.
2. **fundamental exact-bin 조건을 진단·완화한다.** 실패 시 각 음의 `centerBin`과
   `strongestBin`을 기록하면 원인을 직접 확인할 수 있다.
3. onset timestamp 기반 판정 창과 잔향 onset 선점은 현재 증거상 후순위다.
