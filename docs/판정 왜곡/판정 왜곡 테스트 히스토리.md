현재까지 확인한 판정 왜곡 히스토리는 이렇게 정리됩니다.

**1. 직렬 구조는 비교적 정상**
`RhythmGame.cpp`처럼 DSP와 Judge가 같은 흐름에서 처리될 때는 대부분 `Perfect/Good`이 나왔고, pitch도 목표 음과 잘 맞았습니다.

**2. SPSC 병렬 구조부터 wrong note가 급증**
`RhythmGame_0.2v.cpp`처럼 audio callback과 judge thread를 SPSC로 분리한 뒤부터 `Miss (wrong note)`가 크게 늘었습니다. 특히 `MIDI 0`이나 이전/주변 음으로 잡히는 경우가 많았습니다.

**3. DLL/클라이언트 구조 문제는 아님**
`RhythmGameDLL.cpp`에서도 이벤트는 CLI에 정상 반영됐습니다. 즉 `PollJudgeEvent()`나 CLI 표시 문제가 아니라, 플러그인 내부 판정 결과 자체가 왜곡되고 있었습니다.

**4. SPSC 포인터 문제는 배제**
모니터링 결과:

```text
pointer alias blocks: 0
changed first sample: 0
```

큐가 input buffer 포인터를 들고 있는 것이 아니라, PCM 데이터를 복사해서 보관하고 있음이 확인됐습니다.

**5. Judge 처리 지연도 주원인은 아님**
큐 지연은 대략:

```text
avg 3.x ms
max 약 18~21 ms
```

정도로 나왔습니다. 이 정도 지연만으로 대량의 wrong note, 특히 `MIDI 0` 발생을 설명하기는 어렵습니다.

**6. 핵심 원인은 onset 시점 pitch 판정 방식**
Onset 테스트 결과:

```text
onset events          : 23
accepted onset events : 18
zero MIDI events      : 16
wrong MIDI events     : 21
```

즉 onset은 잘 잡히고 타이밍도 판정창 안에 들어오지만, 그 순간 pitch가 `0`이거나 이전/주변 음으로 잡힙니다.

현재 구조는:

```cpp
aubio_pitch_do(...)
lastDetectedMidi = round(pitch)

aubio_onset_do(...)
if onset:
    lastDetectedMidi로 판정
```

인데, 이 방식은 onset 직후 attack 구간에서 안정되지 않은 pitch를 그대로 사용합니다.

**현재 결론**
판정 왜곡의 주원인은 SPSC 복사나 큐 지연이 아니라, **onset 발생 순간의 pitch를 즉시 사용하는 구조**입니다.  
다음 개선 방향은 onset 후 몇 ms 또는 몇 블록 동안 pitch 후보를 모아서, `MIDI 0`을 제외하고 안정된 pitch로 판정하는 방식입니다.
